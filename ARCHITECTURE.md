## 1. Общая концепция — каскадная маршрутизация запросов

Система построена по принципу **каскадного роутера** с тремя уровнями обработки запросов. Уровни применяются последовательно, пока не будет получен удовлетворительный ответ:

1. **RAG (векторный поиск в базе знаний)** – приоритетный уровень.  
2. **Локальная LLM (Ollama)** – если RAG не дал результата.  
3. **Облачная LLM (Anthropic Claude)** – финальный уровень, если локальная модель не справляется.

**Жёсткое правило:** облачный уровень вызывается **только** если локальный уровень явно запросил эскалацию или произошла ошибка. Это минимизирует затраты на API и обеспечивает конфиденциальность данных.

2.3 Локальная LLM (local_llm.py)
Класс LocalLLMClient с методом analyze_and_generate(prompt: str) -> dict:

отправляет запрос в Ollama;

возвращает JSON: can_answer (bool), reason (str), response (str).
Модель получает системный промпт, который заставляет её оценить свою компетенцию перед генерацией.

2.4 RAG-движок (rag_engine.py)
Класс RAGEngine (ChromaDB + sentence-transformers):

add_documents(texts, metadatas)

query(prompt: str) -> dict – возвращает найденный контекст и максимальный балл релевантности; если балл ниже RAG_SCORE_THRESHOLD > found=False.

Алгоритм RAG:

Запрос > эмбеддинг.

Поиск ближайших соседей в ChromaDB.

Если найдены документы с баллом ? порога > формируется контекст, ответ генерируется локальной моделью с этим контекстом.

Иначе > сигнал для перехода к локальному уровню.

2.5 Облачная LLM (cloud_llm.py)
Класс CloudLLMClient (SDK Anthropic) с методом generate_response(prompt: str, context: str = None) -> str.

Если передан контекст, он добавляется в системный промпт.

Облачная модель используется только когда локальный уровень не смог ответить (или явно запрошено пользователем).

2.6 Каскадный роутер (router.py)
Класс CascadeRouter, метод process_query(prompt: str) -> dict:

Шаг RAG:

rag_engine.query(prompt) > если found == True, то вызывается локальная модель с контекстом RAG, ответ возвращается с source: 'rag'.

Шаг Local:

Если RAG не дал результата, вызывается local_llm.analyze_and_generate(prompt).

Если can_answer == True, ответ возвращается с source: 'local'.

Шаг Cloud:

Если локальная модель не может ответить или вернула маркер [NEED_CLOUD], вызывается cloud_llm.generate_response(prompt) с source: 'cloud'.

Ответ всегда содержит: text, source, context_used (bool), и логи выполнения.

2.7 CLI (main.py)
Поддержка индексации тестовых документов.

Интерактивный цикл с цветным выводом уровня источника.

4. Расширенные бизнес-требования
4.1 Сохранение диалогов в RAG (Knowledge Auto-Harvesting)
Кнопка [?? Сохранить в Базу Знаний] (доступна админу/инженеру) > связка «вопрос + ответ» отправляется в локальную LLM для генерации краткой инструкции (Markdown-карточка) и загружается в ChromaDB.
В будущем аналогичные запросы будут решаться через RAG без облачных вызовов.

4.2 Управление окном памяти (Context Pruning)
По умолчанию хранится последние 20 сообщений диалога (настраивается админом).

При превышении 70% контекстного окна модели (токены) выполняется сжатие:

Берётся блок старых сообщений (например, с 1-го по 35-е).
Локальная модель формирует краткую сводку (3–5 предложений).
Старый блок заменяется плашкой [Сводка предыдущей беседы: …], последние 15 сообщений остаются.
История в БД хранится полностью, но в сессию передаётся сжатая версия.
4.3 Business Rules Engine (динамические правила)
Команда админа: /add_rule <текст правила>.

Хранение: таблица business_rules в PostgreSQL.

При каждом расчёте/диалоге правила подмешиваются в системный промпт локальной модели и в RAG-контекст.

При нарушении правила – выдаётся предупреждение со ссылкой на регламент, но действие разрешается.

4.4 FSM-калькуляторы (пошаговые мастера)
Расчёт потребления и кабелей
Вход: тип экрана, размер (Ш?В), яркость, модель модуля.
Выход: мощность (кВт), номинал автоматов (А), сечение кабелей, количество БП с запасом 20%.

Расчёт количества модулей
Вход: габариты экрана, шаг пикселя (P1.8/P2.5/P3.91/P4.81) или размер модуля.
Выход: количество модулей по горизонтали/вертикали, разрешение (W?H), площадь, пропорции.

Сводка по складу – интеграция с учётной системой (парсинг остатков модулей, контроллеров, БП, кабелей).

Подбор комплектующих – полный конструктор: экран + каркас + отправляющие/приёмные карты + БП + кабели + видеопроцессор.

4.5 Генерация КП и смет (Sales & Spec Generator)
После завершения подбора комплектующих – кнопка [?? Сформировать КП].

DOCX: коммерческое предложение с логотипом, составом оборудования, гарантией.

XLSX: смета для внутреннего использования (закупочные цены, маржа, итоговая стоимость).

4.6 Работа с PDF-спецификациями (Multi-modal PDF RAG)
Загрузка PDF/даташитов через Telegram или Web UI.

Извлечение текста и таблиц (PyMuPDF + pdfplumber).

Индексация в ChromaDB (выборочно, по категориям – критерии будут уточнены на этапе обучения).

Инженер может задать вопрос по документу («Какой приёмник нужен для этого модуля?»), ответ приходит из RAG.

4.7 Инженерный диагностический помощник
Интерактивное дерево устранения неисправностей:

Симптомы: «Гаснет часть кабинета», «Полосы по вертикали», «Ошибка связи в NovaLCT».

Бот выдаёт пошаговые инструкции (проверка кабелей, питания, прошивки) с картинками из базы знаний.

4.8 Доступ и аналитика – финальное решение
Единый уровень доступа: все сотрудники имеют доступ ко всем данным (база знаний, калькуляторы, проекты).

Административная панель: статистика по каждому пользователю (количество запросов, расчётов, соотношение Local/RAG/Cloud, затраты на API) доступна только админам (список ADMIN_IDS).

Оценка затрат на облачный API (токены, стоимость) логируется в Langfuse и отображается в админ-панели.

4.9 Создание пользователей
Команда /add_user (только админ) – ввод Telegram ID/Username, имени, должности.

Генерируется инвайт-ссылка/ключ для доступа к боту и веб-интерфейсу.

Единая учётная запись для обоих каналов.

5. Веб-интерфейс (Web UI)
Решение: использовать Open WebUI как готовый веб-интерфейс, проксируя все запросы через FastAPI-бэкенд.

5.1 Архитектура интеграции
Open WebUI подключается к FastAPI как к единому бэкенду (переопределение эндпоинтов /api/chat и др.).

Все запросы проходят через FastAPI, который:

управляет аутентификацией (JWT);

вызывает каскадный роутер;

хранит историю диалогов в PostgreSQL (единая с Telegram).

Open WebUI используется только для рендеринга UI, не имеет прямого доступа к БД.

5.2 Функционал веб-интерфейса
Боковая панель с историей чатов и «Блокнотами» (проектами).

Прикрепление PDF-документов к проектам – RAG в рамках проекта использует только эти документы.

Экспорт сметы в DOCX/XLSX в один клик.

Индикатор источника ответа: [?? RAG] / [? Локальная] / [?? Claude].

Административная панель (аналитика, управление правилами) – только для админов.

5.3 Аутентификация (SSO)
Пользователь в Telegram нажимает кнопку «Войти в Web».

Бот генерирует одноразовый токен (OTT) со сроком жизни 5 минут.

Пользователь переходит по ссылке на Open WebUI, где токен обменивается на JWT.

JWT действует 8 часов, поддерживается refresh-токен (в Redis).

6. Групповые чаты Telegram — напоминания и активность
6.1 Правила поведения в группах
Бот отвечает только при упоминании (@bot_username), reply на сообщение бота, или по команде /remind.

Без упоминания – бот молча логирует сообщение для аналитики.

6.2 Smart Reminders Engine
Обычные напоминания: /remind 15:00 Проверить блоки питания.

NLU-напоминания: распознавание естественного языка через локальную LLM (пример: «напомни завтра в 10 утра скинуть смету Николе»).

Периодические: cron-выражения (например, каждую пятницу в 17:00).

Адресаты: можно тэгнуть конкретного участника (@username).

6.3 Live Activity Tracking
Учёт времени последнего сообщения, количества обработанных задач.

/today – сводка активности в группе за день (доступна админу).

Автоматический вечерний дайджест (опционально).

Используется APScheduler (AsyncIOScheduler).

При старте загружаются все невыполненные напоминания.

Каждую минуту проверяются задачи, срок которых наступил.

Отправка сообщения с инлайн-кнопками [? Выполнено] и [? Отложить на 15 мин].

6.6 NLU-парсер напоминаний (core/reminder_parser.py)
Сначала – базовые regex и dateparser.

При сложной формулировке – вызов локальной LLM с требованием JSON-ответа:

json

  "target_username": "@nikolia",
  "task_text": "Скинуть смету по объекту"
}
Часовой пояс – UTC+3 (Минск).

6.7 Group Handlers и Middleware
GroupActivityMiddleware – обновляет last_seen, отправляет краткий лог в activity_logs.

Хэндлеры для обработки добавления бота в группу, команд /remind, /today.

8. Правила написания кода
Строгая типизация: Pydantic V2 схемы, Type Hints (Optional, List, Dict).

Async/await для всех I/O (БД, HTTP, Telegram API, Ollama).

Модульность: хэндлеры > сервисы > репозитории; бизнес-логика не в хэндлерах.

Обработка ошибок: graceful degradation – при недоступности Ollama или Claude возвращается осмысленное сообщение, система не падает.

Логирование: Loguru с указанием user_id и chat_id.

Тестирование: PyTest для модулей и интеграционных сценариев.
