# Open Source стратегия и план развития RAG

**Версия:** 2.0 (объединённая и актуализированная)  
**Дата:** 2026-08-09

---

## 1. Цель документа

Закрепить выбор Open Source компонентов для инфраструктуры ИИ-системы «Папай», определить границы их использования, а также зафиксировать план развития RAG (Retrieval-Augmented Generation) с акцентом на качество, наблюдаемость и визуализацию.

Главный принцип: готовые Open Source проекты используются как **инфраструктура**, а уникальная бизнес-логика (Cascade Router, Business Rules, FSM-калькуляторы, проекты, права доступа, единая история) реализуется **собственным кодом** на FastAPI.

## 3. Компоненты, которые **НЕ** используются в ядре

Следующие проекты исключены из основного стека на первом этапе, чтобы избежать излишней абстракции и потери контроля над архитектурой:

- **LangChain**
- **LlamaIndex**
- **Haystack**
- **CrewAI**
- **AutoGen**
- **RAGFlow** (используется только как исследовательский стенд позже)
- **Dify** (используется только для прототипирования позже)

**Исключение:** отдельный фреймворк может быть добавлен на этапе 5, если конкретная задача (например, сложные агентные цепочки) действительно неудобна для собственного кода.

## 4. Решение по владению данными (Open WebUI)

**Open WebUI используется ТОЛЬКО как интерфейсный слой.**  
Вся бизнес-логика, управление пользователями, проектами, историей и файлами находится под контролем **FastAPI-бэкенда**.  

- Open WebUI не имеет прямого доступа к PostgreSQL, Redis или ChromaDB.
- Все запросы от Open WebUI проксируются через FastAPI.
- Аутентификация и сессии управляются FastAPI (JWT), Open WebUI подключается через SSO (OTT > JWT).

## 5. План развития RAG (этапы)

### Этап 1: Core RAG (базовая функциональность)
- Интеграция ChromaDB с эмбеддингами (Sentence-Transformers).
- Загрузка документов (PDF через PyMuPDF + pdfplumber, OCR через OCRmyPDF при необходимости).
- Базовый поиск с порогом `RAG_SCORE_THRESHOLD = 0.65`.
- Выдача контекста локальной модели для генерации ответа.

### Этап 2: Надёжность и управление знаниями
- Разделение знаний на **project-level** и **global-level**.
- Валидация и утверждение знаний перед индексацией (процесс согласования).
- Версионирование документов.
- Автоматическое сохранение диалогов в БЗ (Knowledge Auto-Harvesting).

### Этап 3: RAG Quality (бенчмаркинг и настройка)
- Создание набора тестовых документов и запросов (benchmark).
- Измерение точности поиска (Recall@K, MRR).
- Тюнинг порога схожести, размера чанков, стратегии чанкинга.
- Внедрение реранкинга (если необходимо).
- Оценка качества ответов с цитированием источников (citation/grounding).

### Этап 4: Визуализация RAG (админ-панель)
Подробнее – см. раздел 6.

### Этап 5: Расширение и исследования
- Использование **RAGFlow** как исследовательского стенда для сравнения качества обработки документов.
- Использование **Dify** для прототипирования визуальных workflow.
- Оценка перехода на **pgvector** (встроенные векторы в PostgreSQL) для упрощения стека.
- Добавление дополнительных парсеров (XLSX, DOCX, изображения).

## 6. Визуализация RAG (административный интерфейс)

Цель: дать администратору/инженеру возможность видеть не только ответ, но и всю цепочку получения ответа из базы знаний.  
Реализуется **собственным интерфейсом** на FastAPI + React/Vue (или как часть админ-панели Open WebUI), без использования тяжёлых RAG-фреймворков.

### 6.1 Что показывать:

| Экран | Содержание |
|-------|------------|
| **Документ** | Метаданные (filename, project, source, version, date), страницы, извлечённый текст, OCR-статус. |
| **Чанкинг** | Документ > список чанков с текстом, номером страницы, размером, ID эмбеддинга. |
| **Эмбеддинг** | Для каждого чанка: модель эмбеддинга, коллекция, метаданные. |
| **Retrieval** | Запрос > эмбеддинг запроса > поиск в ChromaDB > список найденных чанков с оценками схожести (score). |
| **Финальный ответ** | Весь трейс: вопрос > решение роутера (RAG/Local/Cloud) > поиск > выбранные чанки > контекст > LLM-запрос > итоговый ответ с ссылками на источники. |

### 6.2 Трассировка запросов (RAG Trace ID)

Каждый запрос получает уникальный `rag_trace_id`. События записываются в Langfuse и/или отдельную таблицу:

1. `document_loaded`
2. `text_extracted`
3. `chunk_created`
4. `embedding_created`
5. `query_embedded`
6. `retrieval_started`
7. `retrieval_results` (список чанков с баллами)
8. `chunks_selected` (Top-K)
9. `context_built`
10. `llm_called` (модель, промпт, токены)
11. `answer_generated`

**Пример трейса в интерфейсе:**
TRACE #A1847
User: "Какой контроллер нужен для экрана P2?"
Router: RAG
Query embedding: model=all-MiniLM-L6-v2
Collection: led_equipment
Retrieved:

NovaStar TB50 — 0.91

NovaStar TB60 — 0.87

MRV316 — 0.79

MCTRL4K — 0.73
Selected: TB50, TB60, MCTRL4K
Context: 3 chunks / 1840 tokens
Generator: Local LLM (Ollama)
Answer: ...

text

Это позволяет быстро выявлять проблемы: неправильный чанкинг, слабый эмбеддинг, неверный порог, плохой Top-K, ошибки в контексте или генерации.

## 7. Приоритет развития (дорожная карта RAG)

| Этап | Задачи |
|------|--------|
| **1. Core** | Внедрение базового RAG (ChromaDB + sentence-transformers), интеграция с каскадным роутером. |
| **2. Надёжность** | Разделение знаний, версионирование, автосохранение диалогов. |
| **3. RAG Quality** | Бенчмаркинг, тюнинг порогов, реранкинг, цитирование. |
| **4. Визуализация** | Реализация трейсов, административный интерфейс. |
| **5. Расширение** | Исследование RAGFlow/Dify, pgvector, дополнительные парсеры. |

## 8. Исследовательские инструменты (не в production)

### 8.1 RAGFlow
- **Цель:** исследование и сравнение качества чанкинга, парсинга, поиска.
- **Использование:** как отдельный стенд для проверки сложных PDF, benchmark собственного RAG.
- **Не интегрируется** в основной пайплайн на этапах 1-4.
- Репозиторий: https://github.com/infiniflow/ragflow

### 8.2 Dify
- **Цель:** прототипирование визуальных workflow и RAG-пайплайнов.
- **Использование:** для быстрого создания прототипов и сравнения архитектур.
- **Не заменяет** FastAPI + Cascade Router.
- Репозиторий: https://github.com/langgenius/dify

## 9. Безопасность зависимостей

- Все Open Source компоненты должны использоваться с **фиксированными версиями** (зафиксировано в `requirements.txt` / `pyproject.toml`).
- Для критических пакетов (например, Anthropic SDK, FastAPI) использовать проверенные релизы и проверять хеши.
- Внедрить регулярное сканирование зависимостей на CVE (например, `safety`, `pip-audit`).
- **LiteLLM исключён** из стека из-за предыдущих инцидентов с компрометацией релизов (выбрано прямое использование Anthropic SDK).
